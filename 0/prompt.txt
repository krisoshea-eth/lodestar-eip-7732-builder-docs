Checked both on unstable:

assertEqualParams → @lodestar/config is right, and it's a clean move: it only imports from @lodestar/config + @lodestar/params already (ChainConfig, SpecJson, chainConfigToJson, deserializeBlobSchedule, activePreset, presetToJson) — zero @lodestar/api dependency. So nothing new gets pulled into config, and validator just re-imports from there. Its private getSpecCriticalParams helper lives in the same file, so the whole util/params.ts moves together.

waitForGenesis is the awkward one — it needs @lodestar/api (ApiClient for api.beacon.getGenesis()), so it can't go in config (wrong dep direction: api depends on config, not the reverse). No shared package currently sits above api, so realistically either:
duplicate the ~12 lines in the builder pkg — it's a trivial poll loop, Marko's "fine to have a duplicate" instinct is reasonable, or
put it in @lodestar/api itself — the one shared pkg that already has ApiClient + sleep/Logger from utils (no new deps), then validator + builder both import it.

I'd lean duplicate unless you want to kill that 5-year-old TODO in the same pass — the // Search for a 404 error which indicates genesis has not yet occurred comment is literally the client half of the bn-404 gap you're already discussing. If the bn starts returning 404 pre-genesis, one shared genesis-aware poller (that distinguishes "not genesis yet" from a real error) beats two copies drifting apart — and that tips it toward a single home in @lodestar/api.
